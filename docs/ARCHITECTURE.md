# Как устроена система

Схемы и объяснение: какие процессы работают, кто с кем разговаривает и когда что происходит. Если нужна только
картинка, смотрите раздел 1; если «почему так», раздел 5.

## 1. Общая картина

```
                         ┌────────────────────────────────────────────────┐
                         │                 ВАШ КОМПЬЮТЕР / СЕРВЕР         │
                         │                                                │
  Пользователь           │   ┌──────────────┐        ┌────────────────┐   │
  (браузер) ─────────────┼──►│  САЙТ (web)  │◄──────►│   БАЗА ДАННЫХ  │   │
                         │   │ Next.js:     │        │  PostgreSQL    │   │
                         │   │ страницы+API │        │                │   │
                         │   └──────┬───────┘        │ единственное   │   │
                         │          │ (при добавл.   │ место, через   │   │
                         │          │  дела: прямое  │ которое сайт и │   │
                         │          │  чтение        │ воркер "общают-│   │
                         │          ▼  источника)    │ ся" друг с     │   │
                         │   ┌──────────────┐        │ другом         │   │
                         │   │  СБОРЩИК     │        │                │   │
                         │   │  Python +    │        │                │   │
                         │   │  Playwright  │        │                │   │
                         │   └──────▲───────┘        └───────▲────────┘   │
                         │          │ запускает              │            │
                         │   ┌──────┴────────────────────────┴─────────┐  │
  Telegram  ◄────────────┼───┤            ВОРКЕР (worker)              │  │
  (бот-API) ─────────────┼──►│  1. ПЛАНИРОВЩИК: читает источники        │  │
                         │   │  2. ДОСТАВКА: шлёт уведомления          │  │
                         │   │  3. БОТ: отвечает на /start             │  │
                         │   └──────────────────────────────────────────┘  │
                         └───────────────────────┬────────────────────────┘
                                                 │ запросы к сайтам
                                                 ▼
                                   Migraciones · RENAPER · Correo · PJN
                                      (внешние сайты-источники)
```

Главная мысль: **сайт и воркер напрямую друг друга не вызывают**. Всё общение идёт через базу данных: сайт записывает
«что отслеживать», воркер читает это и записывает «что изменилось», потом отправляет в Telegram.

## 2. Процессы

| Процесс | Где в коде | Что делает | Как часто |
|---|---|---|---|
| **Сайт** (web) | `apps/web` | Страницы, кабинет, админка, API. Принимает платежи, регистрирует, добавляет дела, отправляет письма (Resend) | по запросам пользователей |
| **Воркер: бот** | `apps/worker/src/bot` | Слушает Telegram и отвечает на `/start` (привязка аккаунта). К источникам **не ходит** | сразу, постоянно слушает |
| **Воркер: планировщик** | `apps/worker/src/trackers/scheduler.ts` | Проверяет, чьё дело «пора читать», и читает его через сборщик | просыпается раз в 60 секунд |
| **Воркер: доставка** | там же | Отправляет в Telegram всё, что накопилось в очереди | раз в 3 секунды |
| **Сборщик** | `services/scraper` | Python: открывает сайт-источник, достаёт статус и этапы, отдаёт JSON | по запросу воркера (и сайта при добавлении) |
| **База** | `packages/db` | Хранит всё: пользователей, дела, снимки, события, очередь сообщений | всегда |

Воркер это один Node-процесс, внутри которого три независимых «занятия» (бот, планировщик, доставка). Они не мешают
друг другу: долгое чтение сайта не задерживает ответы бота и уведомления.

## 3. Что происходит, когда вы добавляете дело

```
Пользователь ── "+ Отслеживание" ──► САЙТ
                                       │ 1. проверяет номер, права и свободное место
                                       │ 2. ПРЕДПРОСМОТР: сразу запускает СБОРЩИК, читает источник
                                       │    и показывает "это ваше дело?" (этапы пока скрыты)
Пользователь ── "Да, добавить" ───────►│ 3. записывает дело в БАЗУ: nextCheckAt = "прямо сейчас"
                                       │    (и сохраняет уже прочитанные данные: второй раз не читает)
                                       ▼
                                     БАЗА
                          (дело лежит с пометкой «пора проверить»)
```

## 4. Что происходит потом: опрос и уведомление (главное)

```
        каждые 60 секунд                       каждые 3 секунды
 ┌───────────────────────────┐          ┌──────────────────────────────┐
 │ ПЛАНИРОВЩИК               │          │ ДОСТАВКА                     │
 │ 1. спросить БАЗУ:         │          │ 1. спросить БАЗУ: есть ли    │
 │    "у кого nextCheckAt    │          │    неотправленные события?   │
 │     уже наступил?"        │          │ 2. отправить в Telegram      │
 │    (не больше 5 за раз)   │          │ 3. отметить "отправлено"     │
 │ 2. если никого: ничего    │          └──────────────▲───────────────┘
 │    не делает (1 лёгкий    │                         │ события
 │    запрос в БД)           │                         │
 │ 3. если есть: СБОРЩИК     │                         │
 │    читает сайт источника  │                         │
 │ 4. сравнить с прошлым     │                         │
 │    снимком                │                         │
 │ 5. изменилось? ──► записать СОБЫТИЕ ─────────────────┘
 │ 6. поставить дело на
 │    следующий раз: nextCheckAt = сейчас + 3 часа
 └───────────────────────────┘
```

То есть расписание хранится **в самом деле**: у каждого дела есть своё время следующей проверки `nextCheckAt`. Раз в
минуту воркер только смотрит в базу «не пора ли кого-то».

## 5. Вопросы и ответы

**Если опрос каждого дела раз в 3 часа, зачем воркер просыпается каждую минуту?**
Потому что дела добавляются в разное время. Если бы воркер просыпался раз в 3 часа, то только что добавленное дело ждало
бы до 3 часов первого чтения, а все дела проверялись бы одним «пиком» в одну и ту же минуту. Сейчас у каждого дела своё
время: добавили в 10:07, значит читаем в 10:07, потом в 13:07 и так далее. Минутное пробуждение дешёвое: это один запрос
в базу, сайты читаются только для тех, у кого время подошло.

**Откуда лимит «не больше 5 за раз»?**
Чтобы не открывать десятки браузеров одновременно и не заваливать госсайты (`TRACKER_CONFIG.batchSize`). Это значит, что
один воркер успевает самое большее 5 дел в минуту, то есть около 900 дел при проверке раз в 3 часа, и то если каждое
чтение быстрое (PJN с капчей и RENAPER с браузером заметно медленнее, а пока идёт чтение, новый круг не начинается).
Когда дел станет больше, лимит и параллельность поднимаем (см. «Нагрузка опроса» в [PLAN.md](PLAN.md)).

**А расписание по каждому источнику, которое мы хотели в админке?**
Пока частота одна на всех (3 часа, константа `checkIntervalHours`). Расписание по источникам (например, RENAPER раз в
час, PJN раз в 6 часов) записано в PLAN: будет храниться в базе и меняться из админки без релиза. Структура уже готова
к этому: время следующей проверки считается в одном месте.

**Какие дела воркер читает?**
Только те, что активны, на которые хватает мест (платных и бонусных), и которые не ручные (ручной источник OCASA сейчас выключен для всех).
Остальные просто стоят и ничего не расходуют.

**Что если источник недоступен?**
Дело получает пометку ошибки и повтор через 30 минут (`retryAfterMinutes`), а не через 3 часа. Пользователь видит
«не удалось получить данные», администратор видит ошибку на странице Sources.

## 6. Таймеры в одном месте

| Что | Интервал | Где задан |
|---|---|---|
| Бот отвечает на сообщения | мгновенно | постоянное прослушивание Telegram |
| Доставка уведомлений | 3 секунды | `deliveryIntervalSeconds` |
| Планировщик ищет, кому пора | 60 секунд | `tickIntervalSeconds` |
| Сколько дел читаем за раз | 5 | `batchSize` |
| Повторная проверка каждого дела | 3 часа | `checkIntervalHours` |
| Повтор после ошибки | 30 минут | `retryAfterMinutes` |
| Чистка устаревших кодов и сессий | 1 час | `PURGE_INTERVAL_MS` в воркере |

Значения лежат в `packages/shared/src/config/trackers.ts`, кроме чистки (она в `apps/worker/src/index.ts`).

## 7. Остальные потоки, коротко

- **Привязка Telegram.** Сайт создаёт одноразовый код → пользователь жмёт Start по ссылке → бот получает `/start код`,
  находит аккаунт по коду, записывает ваш Telegram, отвечает «Готово» и присылает последние этапы дел.
- **Оплата и места.** Сайт создаёт платёжный интент в базе → провайдер (сейчас тестовый) подтверждает → общий модуль
  мест (`core.capacity`) решает, сколько дел покрыто платными, бонусными и пробным местами. Воркер читает только
  покрытые дела.
- **Админка.** Тот же сайт, раздел `/admin`, права по ролям; каждое изменение пишется в журнал.

## 8. Где что лежит

```
apps/web         сайт: страницы, API, админка
apps/worker      воркер: бот, планировщик, доставка, команды (создать админа)
packages/core    вся бизнес-логика (дела, места, подписка, платежи, админка)
packages/db      схема базы и миграции
packages/shared  общий конфиг, словари языков, проверка данных
packages/ui      общие компоненты интерфейса
services/scraper сборщик на Python
```

Правило: страницы и обработчики только собирают, а логика лежит в `packages/core`; и сайт, и воркер вызывают одно и то
же ядро.
